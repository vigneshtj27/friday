# Decisions and their reasons

Choices the brief left open, made while building. Each can be changed; the reason is here so you can judge.

| Area | Choice | Why |
|---|---|---|
| Language / server | Python 3.12+, FastAPI, uvicorn | Playwright, Patchright and nodriver are all Python-first; one language end to end. |
| Database | SQLite (WAL) | Single user, single host. No server to run or secure. |
| Encryption | libsodium via PyNaCl, XChaCha20-Poly1305 AEAD | Authenticated; random 192-bit nonces are safe; the secret's name is bound as associated data so a ciphertext copied to another row will not decrypt. Purpose-specific subkeys (secrets, files, sessions) are derived with BLAKE2b. |
| Master key | `FRIDAY_MASTER_KEY` env, or the OS keyring | As the brief asked. Docker uses the env var. |
| Profile encryption at rest | Rely on volume encryption (FileVault / LUKS / gocryptfs) and check for it | Chrome needs plain files while it runs, so app-level encryption of a live profile is not possible. `FRIDAY_VOLUME_CHECK=require` refuses to open a profile on a volume it cannot confirm is encrypted; inside Docker you assert it with `FRIDAY_VOLUME_ENCRYPTED_ASSERT=true`. |
| Remote view | Xvfb + x11vnc (localhost only) + noVNC, bridged through the authenticated app over WebSocket | VNC shows the whole display: native dialogs, permission prompts and the address bar, which a CDP screencast cannot. The VNC port is never exposed; the app's WebSocket checks the session cookie and Origin. A random VNC password per session adds a second lock. noVNC is vendored, not loaded from a CDN. |
| macOS | Native window instead of Xvfb | For development. The handoff page says "use the Chrome window on the host". |
| Driver default | `playwright` (Google Chrome, `channel="chrome"`, headed) | Honest, no stealth patches. |
| `patchright` | Available, opt-in per profile or globally; audited as `stealth=true` | Rule 4: only after a diagnosis says so. |
| `cdp` driver | Chrome started as a plain process, Playwright attaches over CDP | Closest to what nodriver does (no automation launch flags), while keeping one page API for the agent's tools. |
| nodriver | Evaluated, not integrated | Separate async API (no Playwright locators, downloads, routing); integrating it means a second implementation of every tool. The `cdp` driver captures its main idea. Observed on Chrome 155: `navigator.webdriver` was `true` with both `playwright` and `cdp`, so `cdp` alone does not hide automation (and this project doesn't try to). |
| Chrome sandbox | On. Playwright disables it on Linux by default; we pass `chromium_sandbox=True`. | `--no-sandbox` is a security downgrade and shows a warning bar real users never see. |
| Sandbox in Docker | A seccomp profile = Docker's default + `clone`/`unshare`/`setns` | Docker's default profile blocks the user namespaces Chrome's sandbox needs. This is far narrower than `seccomp=unconfined` or `--cap-add SYS_ADMIN`, and the container runs with `cap_drop: ALL` and `no-new-privileges`. `FRIDAY_CHROME_SANDBOX=false` exists as a last resort and is logged on every open. |
| Locale/timezone | `TZ` env + `--lang`/`LANG` for the Chrome process, not Playwright's emulation overrides | What the page sees is what this Chrome genuinely is. On macOS Chrome ignores `--lang`; the `cdp` driver passes `-AppleLanguages`, which the Playwright driver cannot (it rejects non-flag arguments). |
| Fonts in the image | Liberation, Noto core, Noto CJK, Noto emoji | Missing glyph coverage is a cheap fingerprint tell and breaks non-Latin pages. |
| Model | `claude-opus-5-5`, adaptive thinking, effort `high`, server-side refusal fallbacks on | Most capable default. Configurable via `FRIDAY_MODEL` / `FRIDAY_MODEL_EFFORT`. History is append-only (the API requires this for thinking blocks); operator updates go in mid-conversation `system` messages, which are also the prompt-injection-safe channel. |
| Policy | Code classifies every interactive tool call: ALLOW / NEEDS_APPROVAL / DENY | Rule 7. Submits are allowed only in sign-in, filter and search forms; anything labelled pay/transfer/payee/save/change/cancel/agree/... needs approval, per action, with a masked screenshot of the page. When unsure, it asks. |
| Navigation allowlist | Enforced twice: in the `goto`/link policy and at the network layer (`context.route`) for any main-frame navigation | Stops page-initiated redirects to other domains, not just the agent's own. Side effect: Playwright routing disables the HTTP cache for that context. |
| Secrets to the model | Never. The model types `secret:<name>`; the injector checks that the secret belongs to the current profile and that the field's own frame is on the site's domains over HTTPS (localhost exempt for the mock bank). | Prevents prompt injection from steering a password into another site or another account's form. |
| OTP codes | Held in memory as single-use ephemeral secrets (5 min), redacted everywhere | "Never reuse or log OTP codes." |
| SMS codes | Ask the owner (portal, Telegram/ntfy/WhatsApp reply, or an Android SMS-forwarder webhook) | As the brief asked. Replies are only accepted from the configured chat/number/token and only resolve a pending request. |
| Gmail | OAuth installed-app flow with PKCE, scope `gmail.readonly`, refresh token in the vault | Match by sender and time after submit. If a site has no configured sender, falls back to searching by site name plus "code/OTP"; set `otp_senders` for reliability. |
| Diagnosis experiments | Page-load probes run automatically (no credentials); the manual-login test runs on request; credential-submitting variants are not automated | Repeated credential submissions can lock real accounts. Probes plus the manual test isolate most causes without that risk. |
| IP geolocation in diagnosis | `FRIDAY_GEOIP_URL` (default `https://ipinfo.io/json`), fetched through the profile's own network path | Needed for the timezone-vs-IP check. It tells that service your egress IP; set it empty to disable. |
| Currency default | `FRIDAY_DEFAULT_CURRENCY=INR` | Your machine's timezone is Asia/Kolkata. Used only when a CSV has no currency column. |
| PDF statements | Text extracted with pypdf, rows extracted by the model with a strict JSON schema, then verified in code (date range, balance continuity, stated totals) | No generic PDF table parser is reliable across banks; the code-side checks catch extraction mistakes. Scanned (image-only) PDFs are not supported. |
| Dedupe | sha256(source, date, amount, direction, normalized description, balance) + occurrence index within the file | Two identical coffees on one day stay two rows; the same statement downloaded twice adds nothing. |
| Rate limits | One worker per profile, one login per site at a time, ≥60 s between logins to a site, exponential backoff (15 min doubling, max 24 h) after blocked/bounced/rejected/captcha | Rule 6. `force` on a run (portal/CLI) skips backoff, and is audited. |
| Home egress | Built-in authenticated CONNECT proxy (`friday egress-proxy`) | Runs on any home machine; bind to the VPN address. Refuses private/LAN targets so it is not a door into your network. |
| `.env.example` | Shipped as `env.example` | A permission rule in this environment blocks writing `.env*` files. Rename it if you like. |
| Typing verification | After typing, read the field back; on a mismatch retype once, then set the value directly; a secret that still mismatches is cleared and refused | Plain Chrome (the `cdp` driver) drops keystrokes for a few hundred ms after a page commits. A truncated password counts as a failed login and can lock a real account. Two identical non-empty results are accepted as the site reformatting input (maxlength, separators). |
| Owner delivery | A built-in chat page (`/chat`), always on; Telegram/ntfy/WhatsApp optional | Nothing leaves the host and there's no third-party account to set up. Cards are drawn from the live approval/OTP/handoff state, so a request answered in the portal shows as answered in the chat. Delivery is a long poll (returns at once on a new message, re-checks card state every second) rather than WebSockets: simpler behind proxies and it reconnects on its own. Owner messages that delivered or look like a code are stored masked. |
| GCP deployment | One Compute Engine VM in asia-south1 running the existing compose stack; separate data disk; secrets in Secret Manager; own VPC with IAP-only SSH; portal via IAP tunnel | Chrome needs a real VM (Cloud Run has no persistent disk or user namespaces). Mumbai gives an Indian egress IP to match Asia/Kolkata. IAP avoids exposing any port while still using your Google login. Label `app=rv-fri` on every billable resource for billing filters. |
| Chat assistant | Claude with eight tools over friday's own state (accounts, runs, transactions, files, what's waiting); effort `low` (`FRIDAY_CHAT_EFFORT`); replies in the background with a typing indicator | Free text should get things done, but the assistant only starts runs; all browsing happens inside the agent loop's policy. It has no approve tool: a page could inject text into a run summary, so approvals stay a human tap. Codes are routed to the waiting sign-in before the model sees the message. History is append-only in memory; after a restart it resumes from a recap of the recent chat. |
| Open-ended `task` runs | A run kind whose goal is the owner's request, executed by the same agent loop | One generic capability instead of per-site features; the read-only policy and approval gate are what make an open goal safe. |
| Activity fetch | A generic `fetch_activity` run: the agent opens the account's activity page and calls `extract_table`; rows are parsed in code from what the page showed, not from the model's retelling | Cards publish only billed statements, so the current cycle exists only on the page. Model-reported rows are a fallback and are kept only when their amount and description appear in the page text the agent read. Where the page is lives in site notes, not code. |
| Card vs bank amounts | `account_type` on activity fetches; on a card a plain amount is a charge and a minus or CR is money back | Banks and cards use opposite sign conventions on screen. |
| Google grants | Separate Gmail (read-only) and Sheets grants from a portal flow; tokens under the reserved `system/` vault namespace | Least privilege per purpose; nothing to run on the server's terminal; a profile's secret prefix can never cover them (a profile named `google.sheets` would otherwise reach `google/sheets/...`). |
| Sheet appends | `values.append` with `INSERT_ROWS`, header-driven columns, skip rows already present, charges only by default, read back after | Never overwrites; re-runs are safe; card payments don't show up as negative spending; the read-back catches locale or format surprises. |
| Tool layer | `friday/tools/`: every capability (browser runs, Sheets, Gmail, Drive, web, files, memory) is a `Tool` with a declared effect; one `ToolRegistry.call` validates arguments, gates, audits and redacts | One choke point makes the invariants hold for every tool, including ones added later. Approval rules live in the registry, not in prompts. |
| What needs an approval card | `send`, `share`, `spend`, `publish`: always. `write` (private to the owner: own sheet, drafts, memory): only when the call writes to something the owner didn't name, or to something other people can see (checked via Drive permissions, failing closed), or when `FRIDAY_APPROVE_PRIVATE_WRITES=true` | Matches the owner's standing instruction that sheet appends are fine while keeping anything visible to others behind a tap. "Didn't name" catches a write steered by an email or web page. |
| Owner-quote rule | Tools that store state on the owner's behalf for later (memory, schedules, the saved expense sheet) need `owner_quote`, checked in code to appear in the owner's own message | Untrusted text (a web page, an email) can't plant a memory or schedule a job through the model. |
| Removing sheet rows | Only rows friday appended (ledger `sheet_rows`), and only if they still hold what friday wrote | Lets "add a test row, then remove it" work without ever giving the model a way to delete the owner's data. |
| Web fetch | Public addresses only, re-checked on every redirect; 2 MB cap; HTML reduced to text | Stops server-side request forgery into the VM, the LAN or the cloud metadata server. |
| One Google grant | `workspace` (Sheets, `gmail.modify`, `drive.readonly`, `drive.file`); the narrower gmail/sheets grants still work; each feature uses the first connected grant that covers it | One consent tap for the assistant, without breaking existing installs. Sending stays gated in code even though the scope allows it. |
| Planner shape | One structured-output call makes the whole plan; steps reference earlier results with `{"$ref": "s1.path"}`; a step whose arguments need reading/judgement gets a small `fill` call; a final call writes the report | Most steps run with no model call at all, so plans are cheap, deterministic and auditable. `fill` covers the cases a reference can't (an amount inside an email). |
| Verification | Each step carries checks evaluated in code against its real result, and tools add their own read-backs (`verified`). The chat's "Verified" line is built only from those; done steps without any are listed as "not independently verified" | The owner can tell what was proven from what was assumed; the model can't claim a verification. |
| Replanning | On a failed call or check, replan with the failure as quoted, untrusted evidence; at most 2 replans, then a blocker message. A denied approval ends the plan with no replan | Bounded effort, no loops, no hallucinated success; "no" means no. |
| Who can start a plan | Only the owner's chat messages (and, in Phase 3, schedules the owner created) | Web, mail and sheet content reaches the planner only as quoted results or failure evidence, never as a request. Memory/schedule writes need the owner's own words regardless. |
| Memory | `friday/memory.py`: facts and decisions from the owner's own words, outcomes written by code after each plan; all current facts plus relevant outcomes go into the planner's context; a newer fact on the same subject replaces the older one; "forget" is a soft delete | Small, inspectable, and the owner controls it. Per-site browsing know-how stays in site notes. |
| Chat while a plan runs | "status" is answered at once from the running plan (no model call); other messages are acknowledged and handled after the current task; codes still go straight to the waiting sign-in | The owner is never left in silence, and one task at a time keeps state simple. |
| Scheduling | A small loop over a `schedules` table inside the app (15 s poll), no APScheduler | Nothing new to deploy or configure; survives restarts because state is in SQLite; a schedule missed while friday was down fires once, not once per missed slot; recurring jobs at most every 15 min. |
| Scheduled jobs | Store the owner's request text; when due, run it through the same planner and tools, with the same approval cards | A job can't do anything the owner couldn't have asked for interactively, and nothing skips a gate because nobody is watching. |
