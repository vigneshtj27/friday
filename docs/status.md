How to run the real-browser tests on Linux without Google Chrome installed:

```bash
FRIDAY_CHROME_EXECUTABLE=/path/to/chrome uv run pytest -m chrome
```

They need `Xvfb` and `x11vnc` on PATH. When running as root (as in some CI containers), Chrome refuses to start sandboxed, so add `FRIDAY_CHROME_SANDBOX=false`. Use that only for tests: the Docker image runs as a non-root user with the sandbox on.

## Not verified

- **Real sites.** No real bank, card, utility or shopping site has been driven end to end. The first run on each site is expected to need a manual sign-in (seed) and may need a diagnosis.
- **Amex end to end.** The first live test (2026-10-20, build 9857f4d) bounced silently, both automated and by hand, from the GCP egress under plain Playwright. Preflight now blocks that state. Still not run: the home egress (`deploy/egress.sh`), the patchright re-pin and re-seed, and the acceptance in `runbook.md` §5. This environment has no access to the deployment.
- **`deploy/egress.sh` against a real tailnet.** The script has been syntax-checked, and the preflight `--json` it reads is tested. Tailscale join, the proxy wait and the in-container egress lookup through the tailnet haven't been run.
- **Typing aid against a real VNC session.** The page and the keysym mapping are in place; key delivery has only been exercised by the existing VNC bridge tests.
- **Google Sheets and Gmail against Google.** The OAuth flow and the Sheets calls are tested against mocks. Real consent, real API responses (formatting of dates/numbers in your sheet's locale) are not yet verified; the read-back check is there to catch a mismatch on the first real run.
- **The real model as planner.** Plans, fills and reports are tested with a scripted model; no plan has been produced by the real API yet. The planner prompt and tool descriptions are the least-proven part of the assistant: expect to tune them on the first real requests. Every safety rule is enforced in code, so a bad plan can fail, but not bypass a gate.
- **Phase 0 on the live deployment.** Not verifiable from here: the Amex profile's driver/locale/proxy settings, the home egress proxy, the Gmail connection and the manual re-seed (see `runbook.md`). `origin/main` also didn't contain the activity fetch and Sheets work when this phase started; it lives on `main-c3c2du`.
- **Google Workspace against Google.** Sheets, Gmail and Drive calls are tested against a fake that mimics their formats; the real APIs (and the one-tap workspace consent) haven't been exercised.
- **Real Amex / HDFC.** The end-to-end acceptance runs against the mock card site. Real activity pages may not be readable as tables; the row-grounding fallback covers that but is unproven on a real site.
- **`task` runs on a real site.** The capability reuses the tested agent loop, but no open-ended task has been run end to end.
- **The real model driving the loop.** The end-to-end tests use a heuristic stand-in. Prompts and tool definitions are exercised only at the wire level.
- **Gmail OAuth against Google.** The PKCE flow and message matching are tested against a fake. The consent screen and refresh-token exchange have not been run against a real Google project.
- **Telegram, WhatsApp, ntfy and SMS-forwarder delivery.** Message formatting and reply acceptance are unit-tested; live delivery is not.
- **Image-only (scanned) PDF statements.** Not supported; see `decisions.md`.
- **A real SIGKILL mid-write.** The Phase 1 crash tests simulate the interruption (a journalled `started` with no `finished`, then recovery), not an actual process kill during the Google API round trip. The no-duplicate guarantee rests on the `sheets_add_transactions` read-back + existing-key skip, which is tested against the fake Google; it has not been exercised by killing the process during a live append.
- **Resume through the chat end to end.** `recover()`, the interrupted-task chat notice, and `task_resume` are unit-tested, but a full restart → owner says "resume &lt;id&gt;" → the stored request replays has not been run against a live browser or real model.
- **The live eval against the real model (Phase 2 §1).** `scripts/live_eval.py` is built and its harness, scoring, injection checks, table and redaction are tested with a scripted model. It has **not** been run against the real Anthropic API from here (no API run was observed), so there is no results table yet and no prompt/tool-description tuning has been done from real failures. The owner runs `uv run python scripts/live_eval.py --out eval_artifacts` and pastes the printed table here. The scoring is deterministic for a given transcript; the model's behaviour on these 20 tasks is unknown until that run.
- **The spend cap against real spend.** The meter and the hard stop are tested with synthetic costs. Real per-call costs depend on the live API's token usage, which has not been exercised here. `model_budget_usd` defaults to 0 (disabled); set it to turn the cap on.
- **Live notification delivery (Phase 5).** The delivery-check logic, the "never silently enable a channel" rule, the daily brief, the expired-reminder listing and the watch stop-on-block are all unit-tested. What is **not** verified here: a real Telegram or WhatsApp message actually arriving on the owner's device (no live token was exercised), and the owner's choice of which single channel to verify end to end — the spec leaves that to the owner. The brief fires on the scheduler's own loop; its once-a-day timing has been exercised by forcing a tick, not over real wall-clock.
- **The spend gate on a real shop (Phase 4).** The caps, the bound approval, the void-on-change, the ledger and the no-auto-retry rule are all tested at the `SpendGate` level with a mock intent and a fake page (the `verify` callback). What is **not** done: wiring `SpendGate.authorise` into the live browser agent loop at the moment of clicking "Pay" (it reads the on-page total through `verify`, which a browser capability must supply), capturing the exact total/items/address from a real checkout, the masking-verified screenshot on the card, and a run against the one real low-risk shop the spec leaves to the owner. The browser policy (`friday/agent/policy.py`) still uses its keyword heuristic as the in-page backstop; the generic money gate is the SpendGate, not yet called from a page click. 3DS/OTP reuse the existing broker (unchanged).
- **Playbook runs on a real site (Phase 3).** The store, versioning, diff, rollback, the owner-only create/edit (quote + tap) and the effect narrowing (a disallowed effect refused, a required effect carded) are all tested through the registry and the chat with a scripted model. What is **not** verified: running a playbook that drives a real browser, and domain-narrowing enforced at the browser layer — `narrow_domains` and `run_constraints` compute the intersection and it is unit-tested, but it has not been threaded into a live browser task or exercised against a real site. The example modules the spec lists (expense ingestion, watches, purchases as playbooks) are not built yet; the layer they sit on is.

## Fixed in this pass

- The Playwright driver ignored `FRIDAY_CHROME_EXECUTABLE` and always looked for Chrome at its default install path. It now uses the configured executable, except when a diagnosis experiment asks for a specific channel.
- The display backend was resolved once, when the app started, so changing `display_backend` later had no effect. It is now read on each use.
- Under the `cdp` driver, Chrome dropped the first 250–400 ms of keystrokes after a page committed, so a typed password lost its first characters. That would have spent a real login attempt with a wrong password. Typing now reads the field back, retypes once on a mismatch, then sets the value directly. A secret that still doesn't match is cleared, and the agent is told nothing was submitted.
- A sign-in form sent by script (fetch/XHR, then a redirect, as American Express does) was classified while its button was still spinning. Playwright's load-state waits return at once when nothing navigates, so the page still showed the login form and the run stopped as `SILENT_BOUNCE`. A submitting click or Enter now waits (up to 20 s) until the page navigates or every request started by the submit has finished. A bounce verdict is re-checked 4 s later before the run stops. Mock bank scenario `xhr` covers both.
